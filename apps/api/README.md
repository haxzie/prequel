# @prequel/api

Every Prequel API, as one Cloudflare Worker on `api.prequel.sh`.

Accounts and teams, the shared library and its uploads, the desktop sign-in
handshake, transcription, analytics, and the waitlist. The Next app in `apps/web` has no
route handlers at all — it is pages and nothing else.

## Why a Worker and not a Next route

Two reasons, and the second is the one that made it not a choice.

**D1 and R2 want bindings.** From Vercel, D1 is only reachable over Cloudflare's
REST API, which is an HTTPS round-trip on every query — paid on every dashboard
navigation, and again on every session check. A Worker gets both as bindings.

**Video does not fit through a serverless function.** Vercel's request body
limit is 4.5 MB and is infrastructure, not something application code can raise.
That limit is why `/api/transcribe` used to cap uploads at 4 MB when OpenAI
itself accepts 25 MB, and it rules out an export ever passing through.

Uploads do not pass through this Worker either. `POST /v1/videos` returns a
presigned PUT and the client talks to R2 directly — a Worker's own body limit is
100 MB, which a two-minute 4K export is comfortably past.

## Layout

```
src/index.ts        the Hono app: CORS, routes, the error floor
src/auth.ts         Better Auth — Google, magic links, teams, invitations
src/middleware.ts   resolves a session cookie *or* a device bearer token
src/db.ts           Drizzle over the D1 binding
src/env.ts          every binding, var and secret this Worker reads
src/lib/r2.ts       presigned upload and playback URLs
src/lib/ses.ts      transactional email
src/lib/ids.ts      row ids, share slugs, tokens, PKCE helpers
src/lib/rate-limit.ts  the transcription allowance, in D1
src/lib/posthog.ts  analytics: who an event belongs to, and the send
src/routes/         one file per domain
migrations/         generated by packages/db, applied by wrangler
```

The schema lives in `packages/db`, because `drizzle-kit` needs it and this
Worker needs it and they are the same definitions.

## Running it

```bash
cp .dev.vars.example .dev.vars      # then fill it in
pnpm --filter @prequel/db generate  # only after changing the schema
pnpm --filter @prequel/api migrate  # applies to the local D1
pnpm --filter @prequel/api dev      # :8787, everything simulated
pnpm --filter @prequel/api test
```

### Two dev modes, and when the local one is not enough

`pnpm dev` simulates D1 and R2 on disk. Fast, needs no Cloudflare account, and
right for almost everything — auth, teams, invitations, the library listing.

**It cannot finish a share.** A presigned URL is a signature over a real R2
endpoint, so an upload always lands in the live bucket, while `complete` HEADs
the local simulation, finds nothing, and answers "the upload didn't finish". The
object is sitting in R2 perfectly intact; the two halves are simply looking at
different buckets.

`"remote": true` on the R2 binding would fix that and is deliberately not set:
the tests read the same `wrangler.jsonc`, so it would point them at the live
bucket — a suite that writes to production storage and cannot run in CI without
a Cloudflare token.

To exercise the upload path end to end:

```bash
wrangler login
pnpm --filter @prequel/api dev:remote   # the whole Worker, on real bindings
```

That writes real objects and real rows. Deleting the video in the dashboard
removes both.

`.dev.vars` holds the secrets; the non-secret configuration is in
`wrangler.jsonc`. Both are listed in the root `.env.example`.

The web app needs `NEXT_PUBLIC_API_URL=http://localhost:8787` in `.env`, which is
what the checked-in example already sets.

## Two clients, one identity

The dashboard sends a session cookie. The desktop app cannot — that cookie is
scoped to `.prequel.sh`, which Electron never visits, and the renderer's CSP
(`connect-src 'self' prequel-media:`) forbids remote requests outright, so every
call comes from the main process. It holds an opaque device token instead.

`authenticate` in `src/middleware.ts` resolves either into the same
`{ userId, teamId }`, so no route handler knows which one it got.

### The sign-in handshake

The only channel between a browser and a native app on macOS is a URL, and a URL
is not private: `open` logs it, and another application can register the same
scheme and be handed it instead. So the link carries a code that is useless
alone.

```
app    → browser   /desktop/auth?challenge=base64url(sha256(verifier))&state=…
browser→ API       POST /v1/desktop/authorize   { challenge }        → { code }
browser→ app       prequel://auth?code=…&state=…
app    → API       POST /v1/desktop/token       { code, verifier }   → { token }
```

The verifier never leaves the app's memory until it is spent. The state is
checked against the sign-in that process started, so a link from anywhere else
is ignored. Codes are single-use and expire in five minutes, and every refusal
answers with the same message — telling "no such code" apart from "wrong
verifier" would confirm to somebody guessing that a code exists.

Tokens are stored as SHA-256. The plaintext exists in the response that created
it and in `auth.json` on the user's Mac, and nowhere else.

## The update feed

`/v1/updates` is what the desktop app's `electron-updater` is pointed at, and it
is the one route group that is neither authenticated nor backed by a binding.

```
app → API   GET /v1/updates/darwin-arm64/latest-mac.yml   → 302 github.com/…/releases/latest/download/…
app → API   GET /v1/updates/darwin-arm64/Prequel-0.0.3-arm64-mac.zip
                                                          → 302 github.com/…/releases/download/v0.0.3/…
app → API   GET /v1/updates/notes?version=0.0.3           → { notes, publishedAt }
```

The redirect route makes **no** subrequest: it reads the version out of the
filename and hands back a `github.com` URL, which resolves the tag itself. That
is deliberate on both counts. `api.github.com` allows 60 requests an hour per
address and a Worker shares one with everything else on Cloudflare, so calling it
on the download path would put an invisible limit on every user's update; and the
updater routinely asks for assets belonging to the version it is _replacing_,
which "resolve the latest release" cannot answer.

`/notes` is the only route here that calls the API, once per check, purely for
the changelog the update window shows. `GITHUB_TOKEN` is optional and only raises
the rate limit. Every failure on that route is `{ notes: null }` with a 200 —
whether an update exists is settled by the channel file, and a second opinion
here could only disagree with it.

Pointing this at a fork is `GITHUB_REPO` in `wrangler.jsonc`.

## Analytics

The desktop app does not talk to PostHog. It posts batches to `POST /v1/events`
and this Worker forwards them, for three reasons: the project token never ships
inside a `.dmg`, the events are enriched with an identity the app is not allowed
to assert about itself, and analytics can be rerouted or switched off without
asking anybody to install a new build.

`POST /v1/events` is the one `/v1` route with no `authenticate` on it. An app
that has never been signed in still launches, and refusing `app_launched` would
throw away the whole pre-sign-in funnel — how many installs get past the Screen
Recording prompt, how many record anything, how many ever sign in. It answers
`202` to everything, including a PostHog outage: the app does not retry, and a
client that surfaced this to a user would be reporting our failure as their
recording going wrong.

**Who an event belongs to** is the part that fails silently. `distinct_id` is the
signed-in `user.id` when the request carries a device token, and
`install_<x-prequel-install>` before that. The two are joined exactly once: the
app's `signed_in` event becomes a PostHog `$identify` carrying
`$anon_distinct_id`, which merges the anonymous install into the account. Issue
that on every batch instead and person merges churn for nothing; omit it and
everything before sign-in stays on a separate person for ever. The rules are in
`toCaptureBatch`, which is pure so that `test/events.test.ts` can assert them
without a network.

The Worker also emits its own events, for the things the app cannot see or
should not be taken at its word about — `video_shared` when the object has
actually arrived at the size R2 reports, `video_viewed` when a stranger opens a
share link, `upload_quota_exceeded`, `device_authorised`.

`POSTHOG_PROJECT_TOKEN` and `POSTHOG_HOST` are **vars, not secrets**: the token
is write-only and already served to every browser that loads the site. Empty
disables analytics outright, which is what an unconfigured deploy should do.
Development uses the same token as production — every event carries an
`environment` property derived from `APP_URL`, so local traffic is filterable
rather than absent.

## Email, and why it will not send at first

SES refuses to send _from_ an address it has not verified, and while the account
is in the **sandbox** it refuses to send _to_ one either. Both failures reach the
app as a 500 on the sign-in form, so check the source rather than guessing:

```bash
node scripts/ses-status.mjs                      # sender, sandbox, identities
node scripts/ses-status.mjs add you@example.com  # start verifying one
```

A verified identity works as sender _and_ recipient, so verifying one address is
enough to send yourself a magic link and click it.

For production, verify the `prequel.sh` **domain** — DNS records rather than a
click — and request production access to lift the sandbox. `SES_FROM` in the
production env is `hello@prequel.sh` and will fail until that domain is verified;
sending Prequel's mail from some other domain would work but costs deliverability,
which is the slow version of the same failure.

## Billing, and the three tiers

Dodo Payments, as **two products** and one team-wide tier derived from them:

| Product  | Env var                           | Price      | Storage |
| -------- | --------------------------------- | ---------- | ------- |
| Pro      | `DODOPAYMENT_PRO_PRODUCT_ID`      | $9 / month | none    |
| Lifetime | `DODOPAYMENT_LIFETIME_PRODUCT_ID` | $29 once   | 5 GB    |

Pro's allowance is a sentinel rather than a cap — `PRO_QUOTA_BYTES` is
`Number.MAX_SAFE_INTEGER`, so the upload check can never refuse it, because the
site says "Unlimited" and a cap dressed up as one is a promise the uploader
eventually breaks.

Both are the whole app. **Storage is the only thing that differs** — nothing is
gated by tier, so no route should ever ask "is this team Pro" to decide whether
a feature exists.

A team may hold both, and a lot follows from that. Pro is a subscription and
lapses; the lifetime licence is a single payment recorded in `purchase` and
never does. So the tier is _derived_ rather than written by whoever noticed a
change:

```
active subscription (or one inside its grace window)  ->  pro
otherwise, a purchase row                             ->  lifetime
otherwise                                             ->  free      (2 GB)
```

`lib/entitlement.ts` holds that, and `applyPlan` is **the only thing in the
Worker that writes `organization.plan` or `storage_quota_bytes`**. Recomputing
rather than assigning is what makes cancelling a subscription drop a lifetime
holder back to their 5 GB instead of to free — the bug that version would have
had is silent, and it takes away something somebody bought.

`POST /v1/billing/checkout` takes `{ plan: "pro" | "lifetime" }` and defaults to
Pro. It refuses per product rather than per team: buying Pro on top of a
lifetime licence is a sale, and only a second subscription (`ALREADY_PRO`) or a
second lifetime licence (`ALREADY_LIFETIME`) is a 409. Both writes are
owner-or-admin through `requireAdmin`, because both spend money.

### `payment.succeeded` is not evidence of a purchase

Dodo fires it for **every** charge it makes, renewals included. `redeem` in
`routes/webhooks/dodo.ts` therefore requires two things before granting the
licence, and both are load-bearing:

- `subscription_id` is null — a renewal carries the subscription it renewed.
- the cart contains `DODOPAYMENT_LIFETIME_PRODUCT_ID` — the opening charge of a
  new Pro subscription arrives carrying the same `metadata.teamId`.

Drop either and every subscriber is handed a lifetime licence every month. It
would not show up anywhere: they are already `pro`, their quota is already the
larger of the two, and the first symptom is a cancellation that does not take.

### `lifetime` is not sent to the Mac app

`GET /v1/desktop/entitlement` answers `pro` for a lifetime team. Builds already
in the field parse two plan values and read a third as "not paid", so sending
the real one puts a paywall in front of somebody who has paid. The app has no
use for the distinction — it exports either way, and storage is decided by the
share endpoint. The mapping can go once 0.0.11 is out of the field.

### The webhook

Register this in Dodo under **Developer → Webhooks**:

```
production   https://api.prequel.sh/v1/webhooks/dodo
development  <tunnel>/v1/webhooks/dodo
```

Subscribed to `subscription.active`, `.renewed`, `.plan_changed`, `.updated`,
`.on_hold`, `.paused`, `.failed`, `.cancelled`, `.expired`, **and
`payment.succeeded`** — which is the only event a one-off product produces, and
so the only way the lifetime licence is ever granted. Leave it unsubscribed and
that product takes money in silence.

It is the only thing that writes a plan. Checkout returns a URL and nothing
else; what this app believes about a subscription came from a signed delivery
rather than from an optimistic write next to a redirect the user may never
follow.

Three things about that verification fail silently if changed:

- The body must be the **raw bytes**. Parse and re-serialise and the digest
  moves.
- `DODOPAYMENT_WEBHOOK_SECRET` is base64 **after** its `whsec_` prefix.
- `webhook-signature` is a space-separated list of `v1,<base64>` pairs, not one
  signature.

A verified delivery always answers 200, including for an event with no handler —
a 4xx makes Dodo retry until it abandons the endpoint, taking the events that do
matter with it. A _failed signature_ is 401 and is deliberately not recorded as
seen, so one forged POST cannot suppress the genuine delivery behind it.

### The cron

One hourly trigger, for the two things no webhook announces: a grace window
closing after a failed renewal, and rows left disagreeing when a team was
created but its membership was not. `wrangler dev` does not fire it — `curl
<dev-host>/cdn-cgi/local/scheduled`.

## Deploying

Pushing to `main` deploys it. `.github/workflows/deploy-api.yml` runs the
Worker's typecheck and tests, applies any new migration, then deploys — in that
order, because a migration here only ever adds and the old code keeps working
against the new schema for the seconds in between. The other order puts new code
in front of a schema without the tables it reads.

It only fires when `apps/api`, `packages/db` or `packages/env` changed, so a
desktop-only push does not restart every isolate for nothing. Use **Run
workflow** for anything the filter misses.

Two repository secrets make it work:

| Secret                  |                                                                         |
| ----------------------- | ----------------------------------------------------------------------- |
| `CLOUDFLARE_API_TOKEN`  | "Edit Cloudflare Workers" template, plus D1 edit                        |
| `CLOUDFLARE_ACCOUNT_ID` | separate, because a token scoped to several accounts cannot infer which |

The **Worker's own** secrets are not among them. They live on the Worker, set
once and surviving every deploy — putting them in CI would mean a second copy of
a payment key in a second place, for nothing:

```bash
wrangler secret put BETTER_AUTH_SECRET --env production
wrangler secret put DODOPAYMENT_API_KEY --env production
wrangler secret put DODOPAYMENT_WEBHOOK_SECRET --env production
# …and the rest of the list in .env.example
```

First time only, and by hand:

```bash
wrangler d1 create prequel                     # put the id in wrangler.jsonc
wrangler r2 bucket create prequel
```

The same two steps the workflow runs, when a deploy has to happen locally:

```bash
pnpm --filter @prequel/api migrate:remote
pnpm --filter @prequel/api run deploy   # `run` is not optional: pnpm has its own `deploy`
```

The bucket must stay **private**. Playback goes through a presigned GET with a
six-hour life, which is what makes a deleted recording actually stop playing.

`R2_BUCKET` must name the same bucket as the `MEDIA` binding in
`wrangler.jsonc`. The binding does HEAD and DELETE; the secret is what presigned
uploads and playback are signed against. Point them at different buckets and an
upload succeeds, `complete` HEADs a bucket the object was never put in, and the
share fails with "the upload didn't finish" — the production version of the
local-dev trap described above, with nothing to say which of the two is wrong.

Google's OAuth client needs `<API_URL>/api/auth/callback/google` as a redirect
URI, character for character — a trailing slash is a `redirect_uri_mismatch`.

## Things that will bite

**The cookie domain.** The dashboard and this Worker share one session because
both are inside `prequel.sh`. An API on any other registrable domain would never
be sent the cookie, and the dashboard would appear signed out the instant after
signing in. Locally the two are `localhost:3000` and `localhost:8787`; cookies
ignore the port, so that works with no domain set at all — which is why
`crossSubDomainCookies` is switched on by whether `APP_URL` is https.

**CORS cannot be `*`.** A browser refuses to send credentials to a wildcard
origin, so the origin is echoed from configuration.

**`nodejs_compat` is not optional.** Better Auth reaches for `node:crypto`, and
without the flag the Worker fails to start with an error that names nothing
useful.

**D1's `exec` splits on newlines.** A statement written across several lines
arrives truncated. Use `prepare().run()` for anything multi-line — the tests do.

**Migrations are generated into this app, not `packages/db`.**
`wrangler d1 migrations apply` resolves `migrations_dir` relative to
`wrangler.jsonc`, so `packages/db/drizzle.config.ts` writes here on purpose.
