# @prequel/recorder

The napi-rs addon. The only bridge between Node and the Rust crates, and the
only compiled artefact the Electron app loads.

```bash
cd packages/recorder
PATH="$HOME/.cargo/bin:$PATH" pnpm build   # writes prequel-recorder.darwin-arm64.node
pnpm test                                   # vitest, against the built addon
```

**Rebuild after changing any Rust that JavaScript calls, or the change is
invisible.** Electron loads the committed `.node`; nothing in `pnpm dev` or
`pnpm ship` rebuilds it for you. A stale addon explains most "I fixed it in
Rust and nothing changed" afternoons.

## What crosses the boundary

Plain data, only. Objective-C objects and `CMSampleBuffer`s never reach
JavaScript — the Node side sees descriptions of things and commands to act on
them.

| Area        | Surface                                                                                  |
| ----------- | ---------------------------------------------------------------------------------------- |
| Permission  | `screenAccessStatus`, `requestScreenAccess`                                              |
| Enumeration | `listTargets`, `listCameras`                                                             |
| Recording   | `startRecording`, `pauseRecording`, `resumeRecording`, `stopRecording`, `recordingState` |
| Export      | `startExport`, `cancelExport`                                                            |
| Reading     | `probeSession`, `captureWallpaper`                                                       |
| Diagnostics | `setLogFile`                                                                             |

`index.d.ts` is generated by napi from the `#[napi]` attributes — it is the
authoritative shape, and it is committed.

## Decisions worth knowing

**One addon, not two.** Export could have been its own `.node`, but a second
one means a second napi target in turbo, a second `asarUnpack` entry and a
second thing to codesign.

**A single recording slot.** `RECORDER` is one `Mutex<Option<…>>`, and so is
`EXPORT`. Only one of each runs at a time, which is what lets the click tap in
`prequel-capture` use a process-wide buffer rather than threading a raw pointer
through a callback that outlives its frame.

**Export runs on a plain `std::thread`, not an `AsyncTask`.**
`AsyncTask::compute` occupies one of libuv's four default threadpool slots for
what can be minutes, and `listTargets` — also async — would starve behind it.

**Progress is throttled to ~10 Hz in Rust**, not in JS. Per-frame at 60 fps for
a five-minute export is 18,000 hops through the main thread. Completion is a
terminal progress event rather than a resolved promise, so there is one channel
and no ordering race between the two.

**Cancellation** flips an `AtomicBool` checked once per output frame, then asks
the writer to cancel — which deletes the partial file rather than leaving an
unplayable MP4 behind.
